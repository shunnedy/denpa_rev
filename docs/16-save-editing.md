# 16. セーブエディタは作れるか

**結論: 作れる。ただし実セーブファイルが1個は必要。**
ROMから取れる情報だけでエディタの「中身を意味のある表示にする」部分は
もう揃っていて、足りないのは**セーブ内のどこに何があるか**だけ。

## 揃っているもの

### 参照データ（[`tools/dbexport.py`](../tools/dbexport.py)）

全テーブルがdocs/04の同一形式なので、レコードの指すプール内文字列を
辿るだけでID→名前の索引が作れる。65テーブル・12,440レコードを
JSONに書き出せる。

| | 件数 | 名前が取れた数 |
|---|---|---|
| `ItemData` | 3,854 | 3,243 |
| `MessageDenpaName`（電波人間の名前プール） | 2,765 | 2,765 |
| `MonsterParameter` | 1,231 | 1,230 |
| `SkillData`（名前＋分類＋説明文） | 405 | 404 |
| `ColosseumDenpa` / `ColosseumDenpaTeam` | 585 / 3×30 | — |
| `LotRareDenpa`（配信・限定枠） | 計157 | 全件 |
| `CounterStop` / `ParameterCap` / `LevelStatusData` / `LevelData` | — | — |

メッセージ表は `(開始, 終了)` でテキストを指すので別経路でデコードする
（名前プールはレコード長8バイト、会話表は12バイト。先頭2ワードが
`(開始, 終了)` なのは共通）。

### 上限値 — `CounterStop`（1レコード24バイト）

```
ff c9 9a 3b   999,999,999   ← 所持金の上限と見られる
9f 86 01 00    99,999
9f 86 01 00    99,999
63             99
46 03 03 1e 03 70, 3, 3, 30, 3
```

### レベル→ステータス — `LevelStatusData`（33レコード × 36バイト）

36バイト = 12バイト × 3系統、各12バイトが **u16 × 6**。
電波人間のステータスは HP / AP / こうげき / ぼうぎょ / すばやさ / かいひ
の6項目で、先頭の値がレベルの区切りになっている:

```
[0] (1,  25,  7,  8, 10,  4) …
[1] (5,  57, 12, 15, 15,  8) …
[2] (15,138, 23, 31, 28, 20) …
[3] (20,179, 29, 39, 35, 26) …
```

### キャラクターのレイアウトの手本

docs/15 の `ColosseumDenpa`（120バイト）が、ROM内でキャラクター1体を
どう持っているかの実例になる。装備6枠がアイテムIDの参照、末尾に
6項目ぶんの値が並ぶ、という形。セーブ側の1体も同系の並びと考えられる。

## 足りないもの: セーブ内の配置

セーブ領域は exheader の記述で **0x500000（5 MiB）**。
手元に実セーブが無いため、所持金・パーティ・手持ち・フラグが
どのオフセットにあるかは**未知**。

## そこを埋めるための道具（[`tools/savetool.py`](../tools/savetool.py)）

セーブエディタを起こすときの定番手順——「ROMから分かっている値を
セーブの中で探す」——を実装した。

```bash
python3 tools/dbexport.py extracted/update_romfs out/db     # 先に参照データ

python3 tools/savetool.py names  save.bin --db out/db   # 名前プールと一致する文字列
python3 tools/savetool.py value  save.bin 1234567       # 所持金などの数値を探す
python3 tools/savetool.py stats  save.bin               # u16×6 の並びを探す
python3 tools/savetool.py items  save.bin --db out/db   # 妥当なアイテムIDの連続
python3 tools/savetool.py strings save.bin              # UTF-16LE の文字列全部
python3 tools/savetool.py diff   before.bin after.bin   # 2つのセーブの差分
```

`names` が特に効く。生成された電波人間の名前は `MessageDenpaName` の
2,765語から付くので、セーブ内でその語に一致する文字列は**ほぼ確実に
手持ちキャラのレコード先頭**。見つかった位置の間隔を集計して
**レコードの刻み幅を自動推定**する。

`diff` はゲーム内で1つだけ操作して保存し、変わった範囲を見る使い方。
これで所持金やフラグの位置が確定できる。

### 検証

[`tools/test_savetool.py`](../tools/test_savetool.py) が、名前プールの
実データ・実アイテムIDを埋め込んだ**セーブ相当のファイルを合成**して
探索ロジックを検証する。6項目すべて通過:

```
ok  植え込んだ名前8件すべてを発見
ok  レコードの刻み幅(0x80)を推定
ok  所持金をu32として発見
ok  ステータス6枠の並びを発見
ok  アイテムIDの連続を発見
ok  差分が2箇所の編集を報告
```

**これは探索ロジックの検証で、ゲームの実レイアウトの検証ではない。**

## 実セーブの入手について

- **Azahar** はセーブを素のファイルで持つので、そのまま渡せる
- **実機**から吸い出したセーブは DISA コンテナに包まれているので、
  セーブマネージャ等で展開してから渡す（このツールはDISAを解釈しない）

セーブが1個あれば `names` と `stats` でキャラのレコード構造が、
2個（何か1つ操作した前後）あれば `diff` で任意のフィールドが特定できる。
そこまで来ればGUIを被せるだけになる。

## 実セーブの構造（Azahar のセーブ1個を解析）

Azahar のセーブ（約1.86 MB、`savedata.bin`、序盤データ）を
`tools/savetool.py sections` で解析した結果。

### 全体レイアウト — 二重バッファ

先頭に **(オフセット, サイズ) の u32 ペアの表**（セクションディレクトリ）が
あり、本体領域（`0x2000`〜`0x14B...`）と**それをまるごとミラーした
バックアップ領域**（`0x14B...`〜末尾）に分かれている。典型的な
ダブルバッファ型セーブで、片方が壊れても復旧できる作り。

| セクション | サイズ | ミラー | 中身 |
|---|---|---|---|
| `0x002090` | `0x4F8` | `0x14BBF4`（34B差） | プロファイル＋プレイヤー名 |
| `0x002588` | `0xFC0` | `0x14C0EC`（69B差） | **アクティブパーティ** |
| `0x003548` | `0x40998` | `0x14D0AC`（0B差） | **電波人間ボックス**（264 KB、序盤なのでほぼ空） |
| `0x043EE0` ほか×8 | `0x7E0` | — | 2016バイトの繰り返し構造 |
| `0x045E60` ほか×17 | `0x288` | — | マップ／島の状態と見られる |

本体とミラーの差分がプロファイルで34バイト、パーティで69バイトだけ
なのは、セーブ時刻（`0x344F78xx` 形式のタイムスタンプが随所にある）と
**セーブ回数カウンタ／チェックサムの疑い**。編集後にこの整合を取る必要が
あるかは、2個目のセーブと突き合わせれば分かる。

### 読めたもの

- **プレイヤー名**: `AZAHAR`（Azaharの既定名）。プロファイル末尾に
  UTF-16LEで入っている
- **パーティ**: `かげとら` と `かげひろ`（序盤の2体）。パーティセクション
  `0x2588` の中にUTF-16LEで並ぶ。名前は名前プール（`MessageDenpaName`）の
  語そのままではなく**各キャラ固有**（`savetool names` の一致が1件だけ
  だったのはこのため＝プレイヤーが付けた名前やカスタム名が入る）

### まだ特定できていないもの（＝あと一歩）

所持金・レベル・手持ちアイテムが**どのオフセットか**は、この1個だけでは
確定できない。理由は単純で、**基準になる値を知らない**ことと、この
セーブが序盤でボックスが空なこと。埋めるには次のどちらか:

1. **既知の値**: いまの所持金、ジュエル数、ある電波人間のレベルを教えてもらう
   → `savetool value savedata.bin <所持金>` で候補オフセットが一発で出る
2. **2個目のセーブ**: ゲーム内で1つだけ操作（ショップで買い物してゴールドを
   減らす等）して別名で保存 → `savetool diff before.bin after.bin` で
   変わった場所＝そのフィールド、と確定できる

どちらか来れば、所持金・ジュエル・レベルの位置を特定して、
値を書き換えて保存するエディタまで通せる。チェックサムがあれば
その計算もそこで判明する。

## ロード関数からの逆算（所持金の正体）

「セーブをロードする関数から逆算した方が早い」という指摘どおり、
`ScriptFlag::GetGold()`（`0x00184C14`）から追ったら、**所持金は
平フィールドではなかった**。値検索が無意味だった理由もこれで分かった。

```c
uint ScriptFlag::GetGold() {
    store = GetVarStore();
    cap   = store.maxOf(0x1a);                 // 上限
    gold  = ReadVar(store, 0x1a) + ReadVar(store, 0x1b);
    return min(gold, cap);
}
```

- **所持金 = 変数 `0x1a` + 変数 `0x1b`**（2つに分割して保持、合計を上限で丸める）
- 上限は `999,999,999`（`CounterStop[0]` と一致）

変数の読み出し（`FUN_002deec8`）は**ビットパック配列からの可変幅ビット
抽出**だった。各変数は「ビット位置」と「ビット幅」を持ち、ビット配列から
切り出す。この定義表が **`flagData.bin`（FlagData、178レコード × 12B）**。

### FlagData レコード（12バイト）

```
+0  u32  最大値／既定値
+4  u32  ビット位置（ROMでは0、ロード時に幅の累積で算出してキャッシュ）
+8  u16  個数（配列変数の要素数）
+a  u8   ?
+b  u8   ビット幅
```

主要変数（`+0` の最大値と `+b` の幅から用途が読める）:

| 変数 | 幅 | 最大値 | 用途 |
|---|---|---|---|
| `0x1a` | 30bit | 999,999,999 | **所持金（上位/下位の片方）** |
| `0x1b` | 30bit | 999,999,999 | **所持金（もう片方）** |
| `0x1c` | 14bit | 9,999 | **ジュエル**（14bitで9999がちょうど入る） |
| `0x1d` | 7bit | 100 | 割合系（個数3000＝ボックス分の配列か） |
| `0x1e` | 7bit | 100 | 同上 |
| `0x07` | 10bit | 1,000 | — |

これで**全178変数の意味と幅が表から引ける**。ストーリーフラグ・各種
カウンタもこの仕組み。変数の値を変えるには、ビット位置にビット幅ぶんの
値を書き込めばよい。

### 残り1歩: ビット配列のセーブ内位置

変数ストアは実行時 `GSdbAccessor`（`*DAT_002ddc68 + 0x1594`）経由で
読まれる。これは**RAM上の構造**で、セーブファイルのどのセクションから
ロードされるか（＝ビット配列のファイル内オフセット）は、セーブ→RAMの
ロード処理を追えば確定する。幅の累積で全変数のビット位置は計算済みなので、
**配列の先頭ファイルオフセットが1つ決まれば、所持金もジュエルも
ビット単位で読み書きできる**。

セクションサイズから単純には一致しなかった（変数ストアが
大セクション `0x40998` 内にあるか、別レイアウトの可能性）。確定は
次のどちらか:

1. ロード処理（GSdbAccessor初期化）をもう一段追う — 純粋に逆算で決まる
2. ジュエルを持っていればその数、または1操作前後の2セーブ — 経験的に即確定

変数モデル自体は割れているので、どちらでも最後のオフセット1個で
エディタが完成する。

### 読み書きプリミティブは特定済み／ファイル位置だけ未確定

ロード側をさらに追った結果:

- **読み** `FUN_002deec8(store, varIndex)` — ビットパック配列から
  可変幅で抽出（`flagData.bin` の幅・位置に従う）
- **書き** `FUN_002ddc78(store, varIndex, value)` → `FUN_002dc124`
- `ScriptFlag::AddGold` は所持金を `var0x1a` と `var0x1b` に書き戻す
  （片方が上限に達したら他方へ繰り上げる2分割方式）

つまり**変数モデルと読み書き手順は完全に判明**し、所持金＝`0x1a`+`0x1b`、
ジュエル＝`0x1c`、全178変数の幅と上限も表から引ける。

残るのはビット配列の**セーブ内オフセット1個**だが、
今回のセーブは**所持金0・ジュエル0の序盤データ**で、対象の変数が全部0。
「抽出値 ≤ 上限」の制約充足でオフセットを総当たりしても、
**0はどの上限も満たすため候補を絞れない**（`0x2000` 起点で違反0になるが
これは全ゼロ領域による偽陽性）。

確定の道は2つ。**どちらもユーザー作業を増やさない方を優先**:
1. ロード処理（シーンローダ → デシリアライザ）をさらに追って、配列の
   ファイル位置を純粋に逆算する ← 解析で完結
2. （補助的に）所持金かジュエルが非ゼロのセーブが1つあれば、
   制約充足が一意に効いて即確定

モデルと読み書きは割れているので、オフセットが決まり次第
エディタは完成する。

### エディタ完成（基底オフセット1個を残して）

- [`tools/varmap.py`](../tools/varmap.py) — `flagData.bin` から全178変数の
  (ビット位置, 幅, 上限, 個数) を書き出す。結果は
  [`data/variables.json`](../data/variables.json)
- [`tools/varedit.py`](../tools/varedit.py) — セーブの変数ビット配列を
  読み書きする。ゲーム内と同じビット抽出・クランプを再現。往復テスト済み
  （ジュエル=9999、所持金=上限999,999,999、隣接変数を壊さないことを確認）

```bash
python3 tools/varmap.py extracted/update_romfs --json data/variables.json
python3 tools/varedit.py save.bin --vars data/variables.json --base 0x3548 get gold
python3 tools/varedit.py save.bin --vars data/variables.json --base 0x3548 set jewels 9999
python3 tools/varedit.py save.bin --vars data/variables.json --find-base
```

変数モデル・読み書き・全変数の意味は完成している。**唯一の未確定定数は
ビット配列のセーブ内バイトオフセット（`--base`）**で、今回の全ゼロ・序盤
セーブでは「値≤上限」がゼロで常に成立するため一意化できない
（`--find-base` が複数候補を出すのはこのため）。所持金かジュエルが
非ゼロのセーブが1つあれば `--find-base` が一意に絞り、そこでエディタが
完全に動く。この1定数以外はすべて揃っている。

## ジュエルは素のu32だった（v1.17.0 セーブで確定）

非ゼロのv1.17.0セーブ（ジュエル99999・ゴールド28）を解析して確定した。

- **ジュエル = オフセット `0x2088` の素のリトルエンディアン u32**。
  99999 をその位置に発見。プロファイルのセクション `0x2050`（0x40バイト）の
  +0x38。**ミラー複製なし**、1箇所だけ
- 所持金28は**素の値としてはファイル内に存在しない** ＝ 所持金は実行時と
  同じくビットパック変数（`0x1a`+`0x1b`、docs参照）で、セーブ内でも
  別管理。ジュエルだけがプロファイルに素で入っている
  （`GetJewel` = var0x1c + プロファイルの値、の後者がこれ）

### チェックサムは無い

ヘッダ `0x04` の `0xF06111D8` は一見チェックサムだが、**v1.0.0 と v1.17.0 の
まったく別物のセーブで同一値**だった → これは固定マジックで、内容の
チェックサムではない。CRC32/sum/xor の各領域総当たりでも一致せず。
よって**ジュエルのu32を直接書き換えてもセーブは壊れない**（Azaharの
抽出セーブは整合性がアーカイブ層で処理され、この平セーブ内に検査は無い）。

### ツール

[`tools/jeweledit.py`](../tools/jeweledit.py):

```bash
python3 tools/jeweledit.py save.bin               # 現在のジュエルを読む
python3 tools/jeweledit.py save.bin 999999 out.bin # コピーに書き込み
```

検証: savedata2（ジュエル99999）を読んで99999、999999に書き換えると
**0x2088 の4バイトだけ変化**し他は一切変わらないことを確認済み。
これで任意のv1.17.0セーブのジュエルを好きな値にして配布できる。

所持金をセーブ側で編集するにはビットパック変数ストアの位置特定が要る
（docs/16 前半）。所持金は docs/18 のチートコードで実行時に対応するのが早い。

## v1.17.0 セーブエディタ完成（所持金・ジュエル・個体・ボックス）

非ゼロのv1.17.0セーブ（ゴールド999,999,999／ジュエル99,984／個体4体）で
全部確定した。

### 所持金・ジュエル（[`tools/moneyedit.py`](../tools/moneyedit.py)）

- **ジュエル** = `0x2088` の素のu32（ミラー無し・チェックサム無し）
- **所持金** = ビットパック変数 `var0x1a`+`var0x1b`（各30bit、上限999,999,999）。
  **変数ストアは v1.17.0 セーブで byte `0x965FF`**。アンカー999,999,999が
  30bitで一意に出た位置から逆算し、2セーブ（gold 28 と 999,999,999）で一致確認

```bash
python3 tools/moneyedit.py save.bin                                  # 読む
python3 tools/moneyedit.py save.bin --gold 999999999 --jewels 9999 --out new.bin
```

書き換えは `0x2088`（ジュエル）と `0x98625`付近（所持金の30bit）だけが
変化することを確認済み。

### 電波人間の個体・ボックス（[`tools/denpaedit.py`](../tools/denpaedit.py)）

**1個体 = 252バイト(0xFC)の自己完結レコード**。手持ち=`0x2588`から16スロット、
ボックス=`0x3548`から。先頭u32が0なら空きスロット（＝そこに有効な252バイトを
書けば個体が増える）。

4個体（Lv5とLv50×3）のステータス照合で判明したフィールド:

| オフセット | 内容 |
|---|---|
| +0x00 u32 | 個体ID（作成順の連番） |
| +0x14 | 名前（UTF-16LE） |
| +0x1c〜 | 体色・アンテナ・顔パーツ・作成者名（外見の遺伝子、未完全解析） |
| +0x78 u16 | HP |
| +0x7a u8 | AP |
| +0x80 u8 | 幸福度 |
| +0x96 u8 | レベル |
| +0x98 u32 | 累計EXP |

こうげき・ぼうぎょ・すばやさ・かいひ・次のEXPは**保存されず実行時計算**
（レベル＋アンテナ＋ビルドから算出）なので直接編集はできない
（レベル／アンテナを変えれば連動して変わる）。

```bash
python3 tools/denpaedit.py save.bin list              # 全個体一覧
python3 tools/denpaedit.py save.bin set p0 level 50 --out new.bin
python3 tools/denpaedit.py save.bin set p0 exp 838798 --out new.bin
python3 tools/denpaedit.py save.bin copy b0 p2 --out new.bin   # 任意個体を手持ちへ複製
```

`copy` はレコード252バイトを丸ごと複製し、衝突しないよう新しい個体IDを
振る。これで**持っている個体を任意のスロットに出せる**。外見まで新規の
個体を作るには +0x1c〜 の外見遺伝子の解析が要る（未完）。

### 注意

- 変数ストアのオフセット `0x965FF` は手元のv1.17.0セーブ2つで一致。
  別構成のセーブでずれる可能性はあるが、`moneyedit` は読み取り表示で
  現在値を確認できるので、gold が正しく出ていれば位置は合っている
- 手持ちは先頭から詰めて埋める（空きスロットのスキャンで認識される想定）

## 続き: レコードの完全解析とフルエディタ

レコードの残り全項目（外見遺伝子、体色と属性耐性、アンテナ、世代、ステータス計算式、
名前と音声、持ち物の所在）は [docs/19](19-denpa-record.md) にまとめた。
`tools/denpaedit.py` はそれを使った完全版に置き換えてあり、持ち物は変数ストアの
var 0x1d（7bit × 3000）で読み書きする。
