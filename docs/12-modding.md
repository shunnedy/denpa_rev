# 12. MODの作りやすさ

結論から言うと、**データMODは今すぐ作れる。コードMODも足場は揃っている。
モデルとテクスチャの差し替えだけが未着手**。

| やりたいこと | 可否 | 根拠 |
|---|---|---|
| ゲームテキストの書き換え | **実証済み** | docs/05 + `tdmpack.py` |
| 数値バランスの書き換え | **実証済み** | 下記の必要EXP改造 |
| イベント・抽選テーブルの書き換え | 可能 | 同じテーブル形式。レコード長を保てばよい |
| 関数の挙動差し替え（実行中） | 基盤あり | docs/07。実機/エミュ実環境での検証は未了 |
| モデル・テクスチャ差し替え | **未着手** | BCHのジオメトリ書き出しが無い |
| 新規コンテンツの追加 | 難しい | リソースIDの登録が必要。`.crr` のCRO署名検証も壁 |

## 実証1: テキスト

`d01_msg` のUTF-16LE本文を書き換えて再構築し、再デコードで確認。

```
あっ！！電波人間だ、めずらしい！  →  あっ！！電波人間だ、テスト成功！
```

制御コード（ルビ・ページ送り・差し込み）を壊さなければ自由に書ける。
**バイト長を変えると後続レコードのオフセットがずれる**ので、
同じ長さに収めるのが安全（レコードは `(開始, 終了)` の絶対オフセットで
本文を指しているため、長さを変えるならレコード配列も作り直す必要がある）。

## 実証2: 数値バランス

`levelData.bin`（`LevelData`、999レコード × 4バイト = 累積必要経験値）の
全レベルを 1/10 にしてみた。

```bash
# 999レコードすべてを /10 にした levelData.mod を作り
python3 tools/tdmpack.py extracted/update_romfs/2135000A out/2135000A \
        levelData.bin=levelData.mod
```

```
元:   Lv1 0 / Lv2 10 / Lv3 30 / Lv4 71 / Lv5 156 / Lv6 275
改造: Lv1 0 / Lv2  1 / Lv3  3 / Lv4  7 / Lv5  15 / Lv6  27
```

再構築したアーカイブは

- 114セクション・内部114エントリすべてが元と同じ名前で読める
- アーカイブIDも `2135000A` のまま
- 改造した値が読み戻せる

レコード長が4バイト固定なのでレイアウトが崩れない。この種の
「既存レコードの数値をいじる」改造が一番安全で、
`MonsterParameter`・`ShopItem`・`lotRareDenpa_*`・`DoubleupProbability` など
バランス系はすべて同じやり方で触れる。

### ファイルサイズの増加

再構築時、LZ10セクションを**リテラルのみのLZ10**で書き直すため膨らむ。

```
2135000A   1,713,980 B  →  2,086,656 B   (+21.7%)
```

LayeredFSはファイル単位の差し替えなので容量制約はなく、実用上は問題ない。
元のサイズに近づけたいならLZ10のマッチャを実装する必要がある。

## 置き方（LayeredFS）

```
<Azaharユーザーディレクトリ>/load/mods/<TitleID>/romfs/2135000A
```

**注意: どのTitleIDに置くかは未検証**。このゲームは本体
`0004000000125D00` とアップデート `0004000E00125D00` があり、
アップデートを当てた状態では**updateのromfsが優先される**。
アーカイブのリソースIDは base と update で違うものがある
（docs/08: リソース番号222種のうち87番号が両方に存在）ので、
**updateに存在するファイル名を差し替える**のが筋。
`2135000A` は両方にあるので実験に向く。

## コードMOD

docs/07の通り、`app/lanai.crs` から **base 783 / update 1101 個の
名前付きシンボルが絶対アドレス付きで**取れている。実行中の差し替えは
vtable（`.data`上の関数ポインタ）を1ワード書き換えるのが最も安全
（JITのブロックキャッシュと命令キャッシュを避けられる）。

差し替えやすそうな入口の例:

```
0x0012DB88  TableBase::GetRecordIndex(unsigned int) const   ← 全テーブル参照の関門
0x002E6D04  GSdbAccessor::GetRecord(unsigned int) const
0x0017F164  ItemCommon::OpenTreasure()
0x001BF0B8  FishingCommon::Execute()
0x001775C0  ScriptMap::SetIslandLevel(unsigned char)
```

`TableBase::GetRecordIndex` を差し替えると、**ROMを書き換えずに
テーブル参照を実行時に捻じ曲げられる**（あるIDの参照を別レコードに向ける等）。
データMODより小回りが効く。

## 向いていないこと

- **モデル・テクスチャ**: BCHはPICA200のコマンドリスト形式で、読み出しは
  RPG3側でOhana3DS経由の実動ルートがあるが、**書き出し（再生成）は無い**。
  差し替えるなら同形状のBCHを用意する必要がある
- **新規リソースの追加**: romfs直下のファイル名＝リソースID（docs/08）で、
  参照する側がIDをハードコードしているため、新IDを足しても誰も読まない
- **`.cro` の自作差し替え**: `.crr` にCROのハッシュがあり `ldr:ro` が検証する。
  実機はLumaの署名パッチで抜けるがエミュは実装依存。3GXプラグインのほうが素直
