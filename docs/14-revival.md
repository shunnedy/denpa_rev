# 14. Ｗｉ-Ｆｉコロシアム復活の構成

docs/13 のプロトコルを使って、`asahina.net` のサブドメインに自前サーバを
立て、Azahar（および実機Luma3DS）のゲームをそこへ向ける。

```
ゲーム (Azahar)
   │  https://wifi.asahina.net/gameserver?req=...&auth_token=...
   ▼
Cloudflare（TLS終端・プロキシ）
   │  cloudflared named tunnel "asahina-net"
   ▼
127.0.0.1:8082   denpa_server.py
```

## URLの差し替えが25バイトで収まる理由

```
https://la1.denpamen.com/    25バイト（元）
https://wifi.asahina.net/    25バイト（新）
```

同一長なので文字列をその場で上書きでき、ポインタも長さも触らない。
**スキームは `https://` のまま**維持している。その制約として
**サブドメインは4文字ちょうど**になる（`https://` 8 + ホスト16 + `/` 1 = 25、
`asahina.net` が11文字なので 16 − 1 − 11 = 4）。

base で23箇所、update で25箇所。IPSのオフセットは展開後の `.code`
（= `code_dec.bin` のオフセット = VA − `0x00100000`）基準で、
これは Luma3DS と Azahar がパッチを当てる対象と一致する。

## 証明書

ゲームは `la1.denpamen.com` の証明書（1334バイトのDER）を**ピン留め**する。
接続先を変えるなら、**新しいホストの証明書を発行したCAに信頼の起点を
張り替える**。ピン留め先を正当なCAに差し替える形で、検証は有効のまま。

`mkpatch.py --cert ca.der` が3箇所を書き換える:

| | base | update |
|---|---|---|
| DER本体 | `0x0044FC20` | `0x004A2C60` |
| ポインタのワード | `0x00288E04` | `0x002AF460` |
| 長さのワード | `0x00288E10` | `0x002AF46C` |

スロット検出は「埋め込み証明書のDERを探す → そのVAを値として持つワードを
探す → 最も近い位置にある長さの定数を探す」で自動化してあり、
base では手で特定した3アドレスと**完全に一致**した。

CAのDERは**1334バイト以下**でなければならない（既存の証明書と同じ枠に
収めるため）。ECDSAの中間CAはおおむね1000バイト未満なので収まる。

## まだ確かめられていないこと

実機・エミュでの動作確認は**していない**。このマシンにAzaharが無く、
外向きHTTPSも遮断されているため。残るリスクは3つ:

1. **証明書が通るか** — ピン留めされた証明書が既定の信頼ストアに
   *追加*されるのか、それを*置き換える*のかを読み切れていない。
   前者なら3DSの古い信頼ストアに今のCAが入っておらず失敗する
   可能性があり、後者なら `--cert` で張り替えれば通る。
   どちらにしても `--cert` を当てるのが確実側
2. **`auth_token`** — 全リクエストに `&auth_token=<値>` が付く。
   値はNNID由来と見られ、アカウントサーバが停止している今は
   空か無効になる可能性がある。サーバ側は無視する実装にしてあるが、
   **クライアントがトークン取得に失敗した段階で中断する**かどうかは未確認
3. **応答フィールドの意味** — `time` / `bonus_tbl` / `rand3` 以外
   （`total` `player_data` `check` `check_party` `current_party`
   `prize_tbl`）は「SUCCESS + 数値かbase64」までしか分かっていない。
   対戦相手の32バイト名と1256バイトのパーティblobの**中身**も未解析なので、
   合成した相手データで実際にバトルが成立するかは不明

2と3は、Azaharのログとサーバ側のアクセスログを見ながら詰めるのが早い。
サーバは未知の `req` に `ERROR,<コード>` を返すので、何を要求されたかは
ログに残る。
