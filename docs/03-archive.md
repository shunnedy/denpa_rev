# 03. hex名アーカイブのコンテナ仕様

romfs 直下の `28480000` のような8桁hex名のファイルが、ゲームデータの実体を束ねている。
実装は [`tools/tdmarc.py`](../tools/tdmarc.py)。

## ヘッダ（0x18 バイト、リトルエンディアン）

```
0x00 u32  フォーマットバージョン   常に 0x0000000A
0x04 u32  アーカイブID            ファイル名のhexと一致（LE格納）
0x08 u32  0
0x0C u32  0x00010000              サブバージョン？
0x10 u32  セクション数 N
0x14 u32  0
```

## セクションレコード（0x1C バイト × N、ヘッダ直後）

```
0x00 u32  タイムスタンプ的な値（最上位バイトは常に 0x00）
0x04 u32  kind（内容種別、下表）
0x08 u32  ペイロードサイズ
0x0C u32  ペイロードオフセット（ファイル先頭からの絶対値）
0x10 u32  1
0x14 u32  1
0x18 u32  ペイロードの展開後サイズ
```

最初のセクションのオフセットは必ず `0x18 + N * 0x1C` になる。
検証例: `28480000` は N = 0x1F1 = 497、`0x18 + 497 * 0x1C = 0x3674` で実測値と一致。

## ペイロードは2種類

1. **標準ZIP** — 先頭が `PK\x03\x04`。deflate または stored。
   ZIPエントリのファイル名がそのままゲーム内のファイル名になる（`enemy_01.bch` など）。
2. **LZ10圧縮された単一データテーブル** — 先頭が `0x10`。

どちらが来るかは kind と一対一ではないが、強く相関する。

| kind | 主な内容 |
|---|---|
| 1 | `.cro`, `.bin`, フォント, シェーダ, テーブル |
| 2 | フォント（`.bcfnt` / `.bffnt` / `.act`） |
| 3 | データテーブル |
| 4 | `.bch`（モデル） |
| 5 | `.ptcl`（パーティクル） |
| 6 | `.arc`（UIレイアウト）, テーブル |
| 10 | `.gsc`（スクリプト） |
| 11 | データテーブル, `.bin` |
| 12 | データテーブル（最多） |
| 13 | `.bch` |

## LZ10（任天堂標準 LZ77 type 0x10、前方向）

```
0x00 u8   0x10
0x01 u24  展開後サイズ（0 のときは 0x04 の u32 が実サイズ、データは 0x08 から）
```

制御バイトを読み、MSB から 8 ビット分を処理する。ビットが 0 なら 1 バイトのリテラル、
1 なら 2 バイト `b0 b1` を読んで `長さ = (b0 >> 4) + 3`、`距離 = (((b0 & 0xF) << 8) | b1) + 1`
の後方コピー。

検証: セクションレコードの「展開後サイズ」と展開結果の長さが全件一致する。
