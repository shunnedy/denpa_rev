# 01. ROMコンテナの展開

対象は GodMode9 等で復号済みの `.cci`（カード吸い出し）と `.cia`（アップデート）。
鍵は一切不要で、すべて平文のパース処理のみ。実装は [`tools/ctr_extract.py`](../tools/ctr_extract.py)。

## NCSD (.cci)

```
0x000      RSA-2048 署名
0x100      マジック "NCSD"
0x120+8i   パーティション i: u32 オフセット, u32 サイズ（いずれもメディアユニット = 0x200 単位）
```

FREE! のパーティション構成:

| # | 内容 | プロダクトコード | タイトルID |
|---|---|---|---|
| 0 | ゲーム本体 (CXI) | `CTR-N-JF7J` | `0004000000125D00` |
| 1 | 電子説明書 | `CTR-P-CTAP` | `0005000000125D00` |

## CIA（アップデート）

```
0x00 u32  ヘッダサイズ (0x2020)
0x08 u32  証明書チェーンサイズ
0x0C u32  チケットサイズ
0x10 u32  TMDサイズ
0x14 u32  metaサイズ
0x18 u64  コンテンツ合計サイズ
```

各セクションは 0x40 境界に整列。**TMD / チケット内のフィールドはビッグエンディアン**で、
署名タイプ（`0x00010004` = RSA-2048 SHA-256）の後に 0x40 整列のパディングが入る。
TMD body + 0x9E にコンテンツ数、body + 0x9C4 からコンテンツチャンク（1件 0x30 バイト、
コンテンツID / index / type / size の順、すべてBE）。

FREE! のアップデートCIA:

| index | コンテンツID | サイズ | 内容 |
|---|---|---|---|
| 0 | `00000012` | 0x6A29000 | 本体パッチ `CTR-U-JF7J` (`0004000E00125D00`) |
| 1 | `00000001` | 0x16E000 | 電子説明書 (`000400000FF3FF00`) |

content type の bit0 が立っていなければ平文NCCHがそのまま並ぶ。

## NCCH

```
0x100      マジック "NCCH"
0x108 u64  タイトルID
0x150      プロダクトコード (16バイト ASCII)
0x180 u32  ExHeader サイズ
0x188      flags[8]  — flags[7] の bit2 (0x04) が NoCrypto
0x1A0 u32  ExeFS オフセット / 0x1A4 サイズ（メディアユニット単位）
0x1B0 u32  RomFS オフセット / 0x1B4 サイズ
0x200      ExHeader
```

ExHeader の 0x0D（SCI flags）の bit0 が立っていれば ExeFS の `.code` が BLZ 圧縮されている。
FREE! は base / update ともに立っている。

## ExeFS

先頭 0x200 がヘッダ。10エントリ × 0x10 バイト（名前8バイト + u32 オフセット + u32 サイズ）、
オフセットはヘッダ末尾（+0x200）から。

| base | update |
|---|---|
| `.code` 0x243F04, `banner` 0x21360, `icon` 0x36C0 | `.code` 0x276E58, `icon` 0x36C0 |

`icon` は SMDH。`0x08 + 0x200 * 言語index` に短い説明(0x80) / 長い説明(0x100) / 発行元(0x80) が
UTF-16LE で入る（言語index 0 = 日本語, 1 = 英語）。

## BLZ（`.code` の後方LZ77）

末尾8バイトのフッタ:

```
-8 u32  下位24bit = 圧縮領域長 enc_len / 最上位8bit = フッタ長 hdr_len
-4 u32  展開で増える分 inc_len
```

- 展開後サイズ = ファイルサイズ + `inc_len`
- 先頭 `ファイルサイズ - enc_len` バイトは非圧縮でそのまま
- 圧縮データは**後ろから前へ**読み進める。制御バイトは MSB から 8 ビット分を処理し、
  ビットが 0 なら 1 バイトのリテラルコピー、1 なら 2 バイトを読んで
  `長さ = (u16 >> 12) + 3`、`距離 = (u16 & 0xFFF) + 3` のコピー
- この 2 バイトは**リトルエンディアンの u16 として読む**（逆方向ストリームなので
  アドレスの大きい側が上位バイトになる）。ここを間違えると即座に壊れる

検証: 別タイトル（電波人間のRPG3）で入手済みの `code.bin` を本実装で展開した結果が
正解の `code_dec.bin` と MD5 一致（`a1fefd2a92f6d983767a49a833a4eb5f`）。

## RomFS

IVFC コンテナ。level3 の本体オフセットは
`align(0x60 + マスターハッシュサイズ, 1 << level3ブロックサイズ)`（0x4C に log2 値）。

level3 ヘッダ（0x28 バイト）: ヘッダ長 / ディレクトリハッシュテーブル (offset, len) /
ディレクトリメタデータ (offset, len) / ファイルハッシュテーブル (offset, len) /
ファイルメタデータ (offset, len) / ファイルデータ offset。

ディレクトリメタデータ 1 件:

```
0x00 u32 親ディレクトリ   0x04 u32 次の兄弟   0x08 u32 最初の子ディレクトリ
0x0C u32 最初のファイル   0x10 u32 同ハッシュの次   0x14 u32 名前長   0x18 名前(UTF-16LE)
```

ファイルメタデータ 1 件:

```
0x00 u32 親ディレクトリ   0x04 u32 次の兄弟   0x08 u64 データoffset   0x10 u64 データ長
0x18 u32 同ハッシュの次   0x1C u32 名前長   0x20 名前(UTF-16LE)
```

名前長・名前のオフセットがディレクトリとファイルで**異なる**点に注意（0x14/0x18 と 0x1C/0x20）。
