# 08. データレコードの内部と残りの形式

## テーブル形式はZIP内の `.bin` / `.dat` にも適用される

docs/04 のテーブル形式は、LZ10セクション専用ではない。ZIPエントリとして
入っている `.bin` / `.dat` も**同じ0x40ヘッダ**を持つ。

| | 件数 |
|---|---|
| テーブルとして妥当 | **776** |
| 別形式 | 5（`vendor.bin` ×2、`MapChipDB.dat`、他2） |

つまりゲームデータは（モデル・音・レイアウトを除き）ほぼ全部この1形式。

## IDと添字の区別 — `0x80000000` の正体（コードで確定）

Ghidraで `TableBase::GetRecordIndex(unsigned int)` (`0x0012DB88`) と
`GSdbAccessor::GetRecord(unsigned int)` (`0x002E6D04`) を読むと、両者が
同じことをしていた:

```c
hdr = this->header;                       // テーブルヘッダ
if (key < 0x80000000) {
    if (key < hdr[0])  return key;        // そのまま添字として使う
} else if (hdr[6] != NULL) {
    for (i = 0; i < hdr[0]; i++)          // IDの線形探索
        if (((u32*)hdr[6])[i] == key) return i;
}
return 0xFFFFFFFF;
```

つまり **`0x80000000` はフラグではなく「この値はIDであって添字ではない」
という識別子**:

| 値 | 意味 |
|---|---|
| `< 0x80000000` | レコードの**添字**（そのまま使う。レコード数との範囲検査のみ） |
| `>= 0x80000000` | レコードの**ID**（`hdr[6]` のID配列を線形探索して添字に変換） |

`hdr[0]` はレコード数（ヘッダ 0x00）、**`hdr[6]` はヘッダ 0x18**
——これまで「ブロック2」と呼んでいたもの——で、**レコードIDの配列**
（u32 × レコード数）だった。

検証: `0x18` のブロックを持つ2,193テーブルすべてで
`サイズ == レコード数 × 4` が成立し、**不一致は0件**。
残り2,935テーブルはこの配列を持たず添字だけで引かれる。
例として `d01_msg`（39レコード）のID配列は

```
0x80000027 0x80000000 0x80000002 0x80000003 0x80000004 ...
```

で全エントリのbit31が立っている（IDとして参照されるため）。

`GetRecordIndex` は直前の検索結果を `this+0x1C`（キー）と
`this+0x20`（添字）にキャッシュする。`TableBase::Attach(u32)` は
リソースIDを `this+0x24` に保存してローダを呼ぶだけ。

これで docs/04 で「bit31は設定済みフラグと推定」と書いていた箇所は
**IDと添字の区別**に訂正される。レコード内に現れる `0x80000004` のような値は
他テーブル（または同テーブル）のレコードへの**ID参照**。

### レコードワードの分布（参考）

base romfs のテーブルから 148,319 ワードを集計:

| 値のパターン | 比率 | 意味 |
|---|---|---|
| `0x00000000` | 47% | 未設定、または添字0 |
| `0xD0D0D0xx` / `0xD0D0D0D0` | 5% | **未初期化の埋め** |
| bit31が立っている | 19% | **ID参照** |
| それ以外 | 29% | 素の値または添字 |

`0xD0` 埋めはビルドツールが未使用領域に書く値で、MSVCデバッグビルドの
`0xCD` に相当する。

## リソースIDの構造（コードで確定）

`GSarchiveManager::LoadResource(u32 id, u32 lang)` (`0x002CD9D4`) が呼ぶ
ID変換関数 (`0x002EDC08`) の中身:

```c
if (id > 0x3FF && (id & 3) != 0) {
    if ((id & 3) == 1)                  id = 0;              // 無効
    else if ((id & 3) == 2 && lang != 0
             && (id & ((1 << lang) << 2)) != 0)
        id = (id & 0xFFFF0003) | ((1 << lang) << 2);          // 言語を1つ選ぶ
    else                                id = 0;
}
```

つまりリソースID（＝romfs直下のhex名）は

```
上位16bit   リソース番号
bit 1-0     タグ  0 = 言語非依存 / 1 = 無効 / 2 = 言語バリアント
bit 15-2    タグ2のときの言語ビットマスク
```

検証: romfsのアーカイブID **309件すべて**の下位16bitが `0000`（294件）か
`000A`（15件）。`0x0A` は タグ2 + 言語ビット1 で、この日本語ROMには
1言語分しか入っていないことと整合する。`0x3FF` 以下のIDは1件もない
（変換関数が素通しする小さいIDは別系統のリソース）。

リソース番号は222種あり、**87番号が base と update の両方に存在**する。
`0x0091` は base に `00910000`（言語非依存）、update に `0091000A`
（言語バリアント）があり、アップデートで言語別に分けたものがある。

## ブロック3 / ブロック4（0x20・0x28）

ほとんどのテーブルでサイズ0。持っているものはレコード数の倍数になり、
しかも2つのサイズが連動する:

| ブロック3 | ブロック4 | 件数 |
|---|---|---|
| `レコード数 × 24` | `レコード数 × 6` | 168 |
| `レコード数 × 8` | `レコード数 × 3` | 112 |
| `レコード数 × 16` | `レコード数 × 4` | 9 |
| 倍数でない | 倍数でない | 271 |
| サイズ0 | サイズ0 | 4,555 / 4,375 |

レコードごとの可変長サブ配列（ブロック3が本体、ブロック4が各レコードの
位置・個数）と見られるが、幅がテーブルによって違うため確定には
各テーブルのアクセサを読む必要がある。

## 完全にデコードできたもの

### `LevelData`（`levelData.bin`）

```
レコード数 999、レコード長 4 バイト
各レコード = そのレベルに到達するまでの累積経験値（u32）
  Lv1 0 / Lv2 10 / Lv3 30 / Lv4 71 / Lv5 156 / Lv6 275 ...
```

レベル上限999まで用意されている。電波人間のRPG3でも同じ構造
（数値だけ違う）だったので、シリーズ共通の持ち方。

### `MapChipDB.dat`

```
0x00 u32   レコード数（121）
以降 121 × 12バイト:
  0x00 char[8]  チップ名（"path00a" など、NUL埋め）
  0x08 u8[4]    各辺の接続種別
```

`4 + 121*12 = 1456` がファイルサイズと完全一致。
例: `path00a (3,3,3,3)` / `path01a (1,3,1,3)` / `path02a (3,1,3,1)` ——
4値は上下左右の接続タイプで、直線路は対辺が揃う。

### `.ctpk` は CTPK ではない

`cec_box_icon.ctpk` と `cec_msg_icon.ctpk` の4件だけ `CTPK` マジックを
持たない。サイズを見ると

```
cec_box_icon.ctpk  4608 B = 48 × 48 × 2バイト/ピクセル
cec_msg_icon.ctpk  3200 B = 40 × 40 × 2バイト/ピクセル
```

で**ヘッダなしの16bpp生テクスチャ**。`cec` はすれちがい通信（CEC）なので、
すれちがい用の箱とメッセージのアイコン。拡張子が実態と合っていない。

## テーブルでないLZ10セクションの分類

全5,635セクションの内訳が確定した:

| 種別 | 件数 |
|---|---|
| データテーブル | 5,128 |
| 名前ハッシュ索引 | 348 |
| 空（0バイト） | 120 |
| SARC | 38 |
| 0x44未満 | 1 |

### 名前ハッシュ索引（348件、未完）

```
0x00 u32        エントリ数 n
以降 n × 12バイト:
  0x00 u32  名前ハッシュ（**昇順にソート済み**＝二分探索用）
  0x04 u32  未解明
  0x08 u32  未解明
以降 データ本体
```

ハッシュが昇順であることは確認済み。`GSarchiveManager::LoadResource(u32, u32)`
や `TableResource` / `MapResource` / `ResourceFileList` / `MapDataResource`
といったテーブル名から、リソースをID（=ハッシュ）で引くための索引と考えられる。

**ハッシュ関数は未特定**。romfs全体から集めた候補文字列 39,619通り
（アーカイブID、ZIPエントリ名、テーブル名、`.gsc` のソースパス、
それぞれ拡張子あり/なし・大文字小文字・basenameの各変形）に対して
CRC-32 / CRC-32-BZIP2 / FNV-1 / FNV-1a / FNV-1a-64 / djb2 / djb2-xor /
sdbm / Jenkins one-at-a-time / ×31 / ×37 / ×65599 / ELF hash の13種を
試したが、キー1,406件に対し**一致0件**。

ただしキーの分布はハッシュらしさを支持する: 下位2bitが
341/349/370/346 でほぼ均等、bit31も735/671でほぼ半々、つまり
**32bit一様分布**。上のリソースID（下位16bitが `0000`/`000A` に限られる）
とは明確に別物で、レコードIDの集合4,287件とも**共通要素0件**。
したがってキーは名前ハッシュかそれに準じる値で、対象文字列か関数が
まだ合っていない、という状態。

後続の2つのu32もサイズ・オフセットとして解釈すると整合しない。

なお実行時側のリソース探索 (`0x002EE834`) は、ロード済みリソースを
`0x400` 未満と以上で2本のリンクリストに分け、さらに赤黒木
（`std::map` 相当）で引く構造で、このディスク上の索引とは別物だった。

## exheader が CRS のセグメント表を裏付けた

docs/07 のシンボルアドレスは `app/lanai.crs` のセグメント表から導いたが、
exheader の記述と**完全に一致**した。独立した2つの出どころが同じ値を示している。

```
.text    0x00100000  838 pages  size 0x34550C
.rodata  0x00446000   71 pages  size 0x046D88
.data    0x0048D000   26 pages  size 0x0198A4
bss size 0x11C02C
```

その他 exheader から:

```
SCI flags 0x03      bit0 = .code がBLZ圧縮、bit1 = SDアプリケーション
savedata size       0x500000（5 MiB）
program / jump id   0x0004000000125D00
core version        2
依存システムモジュール  31件
```
